# Taste — User Preferences
- Prefers communication in Indonesian (Bahasa Indonesia) for grill/planning sessions and architecture discussions. Confidence: 0.9
- Wants the assistant to research first (web search, read local files, verify facts) before asking questions — never grill from assumptions. Confidence: 0.9
- Strongly prefers the Anthropic `grill-me` pattern: one question per turn, not a batch. Confidence: 0.95
- Wants 2-3 options per question, each with one explicit best recommendation and reasoning. Confidence: 0.95
- Wants the option list to be project-specific and sharp — explicitly anti "AI slop" (no generic boilerplate, no over-abstraction, no empty validation). Confidence: 0.95
- Each question should name its place in the decision tree ("why Q2 not later") and surface the downstream consequence of each option. Confidence: 0.9
- Cares about preventing junior devs and AI agents from writing application code in the wrong place — wants clear structural boundaries (e.g., `src/` fence for app code) as guardrails, not just style. Confidence: 0.9
- Values "minimal change" / "sedikit arsitektur" framing over rewrites — prefers the smallest rearrangement that achieves the stated goal. Confidence: 0.85
- Architecture decisions should be justified with the user's own reasoning chain (e.g., citing project invariants like "Executable Scope" from CONTEXT.md) rather than generic best practices. Confidence: 0.85
- Appreciates and values honest pushback from the assistant when the user makes a choice reflexively or against recommendation — explicitly thanked the assistant for "menjadikan sesi lebih bernilai" when assistant pushed back on reflexive choices. Wants the assistant to call out flip patterns (e.g., "you've now flipped from my recommendation twice") rather than silently locking in suboptimal decisions. Confidence: 0.9
- Will self-correct reflectively when shown concrete trade-offs ("aku reflektif tadi" after re-studying options) — the user benefits from explicit trade-off breakdowns and admits reversible mistakes. Trust the user's reflective answers over their first instincts. Confidence: 0.85
- Values "rapi dan mudah dimengerti" (clean and easy to understand) as a real architectural value, but when it conflicts with added complexity (extra layers, indirection, interface wrappers for single implementations), will accept simplicity over ceremony. Frame trade-offs in terms of "what you pay for what you get". Confidence: 0.8
- Prefers placing primitive data types (e.g. `Offset struct`) in the **producing** package, not in a shared `types/` dump package. Rejects the `core/types/` "landfill" anti-pattern. Confidence: 0.85
- Prefers separating infrastructure that has cross-cutting consumers or independent lifecycles into its own package (e.g. `core/crypto/` for AES-GCM and `app.key` lifecycle, not inlined into `catalog/`). Justification: lifecycle is shared by multiple features (Smart Recovery modal is cross-cutting), so the package should not be owned by a single feature. Confidence: 0.85
- Thinks in terms of layered architecture with explicit import direction: `core` (infra) → `platform` (Wails-aware infra) → `features` (user-facing workflows) → `app` (assembly). Values clear layer semantics over flat structure when responsibilities differ in coupling. Confidence: 0.8
- Explicitly values **unit testability without framework runtime** as an architectural decision driver. Chose 3-layer `core`/`platform`/`features` over a flatter layout specifically because it lets `core/` be tested with plain `go test ./core/...` without Wails runtime. Will pay an extra folder layer for the ability to test infrastructure in isolation. Confidence: 0.85
- When explaining unexpected/messy input (e.g. accidental spam, connection errors), gives a brief one-line factual reason rather than dwelling — prefers to move forward quickly once the cause is clear. Confidence: 0.7
- Prefers explicit step-by-step git workflow control: will request branch creation as a separate step before committing, and explicitly defer push until confirmed ("push kita tunda dulu sampai Anda konfirmasi"). Treats `git commit`, `git push`, and `bd dolt push` as distinct checkpoints that should not be bundled together. Confidence: 0.85
- Comfortable with casual/vibe-y branch names (`new-vibe`) rather than strictly semantic ones — branch names are working labels, not documentation. Confidence: 0.7
